# Git 협업 컨벤션

## 1. 기본 원칙

- `main` 브랜치에는 직접 push하지 않는다.
- 기능마다 브랜치를 만들고 PR(Pull Request)로 병합한다.
- 한 커밋에는 한 가지 변경만 담는다.
- 하루에 최소 한 번은 PR을 올려 작업을 작게 나누어 자주 병합한다.
- 브랜치를 3일 넘게 혼자 보유하지 않는다.

## 2. 브랜치 전략

| 브랜치 | 용도 | 예시 |
| --- | --- | --- |
| `main` | 발표·배포용이며 항상 실행 가능한 상태를 유지한다. | - |
| `develop` | 기능을 모아 통합한다. | - |
| `feature/기능명` | 기능 개발에 사용하며 `develop`에서 분기한다. | `feature/question-list`, `feature/auth-login` |
| `fix/버그명` | 버그 수정에 사용한다. | `fix/pagination-offset` |

## 3. 커밋 메시지 규칙

커밋 메시지는 `타입: 무엇을 했는지` 형식으로 작성한다.

| 타입 | 의미 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 | `feat: 질문 목록 페이징 API 추가` |
| `fix` | 버그 수정 | `fix: 답변 채택 시 is_solved 미반영 수정` |
| `refactor` | 동작 변경 없는 코드 정리 | `refactor: 질문 서비스 함수 분리` |
| `style` | 포맷, 세미콜론 등 | `style: prettier 적용` |
| `docs` | 문서 | `docs: DB 명세서 v1.1` |
| `chore` | 설정, 패키지 | `chore: nodemon 추가` |

## 4. PR 규칙

1. 작업 전에 `develop`을 pull 받은 뒤 브랜치를 만든다.
2. PR 제목은 커밋 메시지 규칙과 같은 형식으로 작성한다.
3. PR 본문에는 다음 내용을 적는다.
   - 무엇을 변경했는지
   - 어떻게 확인했는지
   - 관련 이슈
4. 팀원 1명 이상이 리뷰하고 승인(Approve)한 뒤 merge한다.
5. 충돌이 발생하면 PR 작성자가 해결한다. 혼자 해결하기 어려우면 해당 파일 담당자와 함께 해결한다.
6. merge한 브랜치는 삭제한다.

## 5. 저장소에 커밋하지 않는 파일

- `.env`는 절대 커밋하지 않는다.
- `node_modules`와 `.env`를 `.gitignore`에 반드시 포함한다.
- 환경 변수 파일은 키 이름만 작성한 `.env.example`을 커밋한다.
- 팀원은 저장소를 clone한 뒤 `.env.example`을 복사하여 자신의 `.env`를 만든다.
